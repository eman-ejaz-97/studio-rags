Three hosts, one website

The site is split across three free services. Vercel runs the pages, Render runs the API, Neon keeps the data. This page shows what each one holds, how a request crosses them, and how code gets there.

Vercel

Runs the website

  • Builds frontend/ on every push to main
  • Renders pages on its servers in Singapore (sin1)
  • Serves the photos in frontend/public/ from its CDN
  • Forwards /api/v1/* to Render
  • Holds API_ORIGIN and SITE_ENV
  • Hobby plan. Does not sleep
Render

Runs the API

  • Builds backend/Dockerfile once CI passes
  • Runs one container: migrations, then NestJS
  • Holds every secret: database URLs, JWT keys, storage keys
  • Checks /api/v1/health/live every few seconds
  • Free plan, Singapore. Sleeps after 15 minutes idle; the next request waits about a minute
Neon

Keeps the data

  • Postgres 18: workshops, sessions, bookings, enquiries, users
  • A private storage bucket, assets, for files later
  • Two addresses: pooled for the app, direct for migrations
  • Free plan, aws-ap-southeast-1 (Singapore)
  • Sleeps when idle and wakes on the first query

1Vercel

Vercel's server calls Render by name

While rendering, Next.js runs on Vercel and needs the API's real address. apiOrigin() reads API_ORIGIN, set in Vercel's project settings to https://studio-rags-api.onrender.com. A deployed build without it fails loudly rather than pointing at a localhost that does not exist on Vercel.

2Vercel

The browser calls Vercel, and Vercel forwards

Code running in the browser uses relative URLs like /api/v1/contact. Vercel matches the rewrite and fetches the same path from Render, then streams the answer back.

Why not call Render directly: login cookies (Phase 3) use SameSite=Lax, and vercel.app and onrender.com are different sites. A cookie set by Render would never be sent from the Vercel page. Through the rewrite, every cookie belongs to one address.

The destination is fixed when Vercel builds. Change API_ORIGIN, then redeploy.

3RenderNeon

Render runs the API; Neon answers its queries

Every route lives under /api/v1. trust proxy tells Express how many proxies sit in front, so req.ip is the visitor and not a proxy. The throttle depends on it, and it is wrong today: see the open issue.

The running API uses Neon's pooled address, which shares a few real connections among many requests. Migrations and the seed use the direct one, because the pooler cannot hold the lock that stops two migrations running at once.

Flow 2

How code gets onto each host

Merge to main and both hosts rebuild themselves from GitHub. There is no upload step.

  1. Your laptopmerge PR
  2. GitHubCI on main
  3. Vercelbuild frontend/
  4. Renderbuild backend/ when green
  5. Rendermigrate, then start
  6. Neonschema up to date
1Render

Render reads render.yaml from the repo

The service is described in code, not clicked together. Two settings decide when it rebuilds: autoDeployTrigger: checksPass waits for GitHub Actions to go green, and buildFilter skips commits that do not touch backend/. A docs-only merge leaves the API alone.

Vercel has no such gate: it builds every push to main. A red frontend build simply does not replace the live one.

2RenderNeon

Each container start migrates, then serves

The free plan has no pre-deploy hook, so the container does it. prisma migrate deploy applies only migrations Neon has not recorded, and is a no-op otherwise. If one fails, set -e stops the container and Render keeps the previous version live.

This is why migrations reach Neon without anyone running them: a merge that adds one applies it on the next start.

3Your laptopNeon

The seed is the one manual step

The seed writes the admin account, six classes and their dates. It runs from your laptop straight to Neon over the direct address, reading the credentials from .env.local in a subshell so they do not stay in your terminal. You type the admin password; it is never stored in a file. Running it twice changes nothing: CI proves that on every push.

Open issue: the throttle cannot tell visitors apart

Must be fixed before the sign-in screens reach staging (SPEC § 10, item 14).

The login throttle allows 10 attempts a minute per visitor. It identifies a visitor by req.ip. Behind proxies, Express works that out from X-Forwarded-For, the list of addresses each proxy appends: it skips TRUST_PROXY entries from the right and takes the next one.

render.yaml assumes two proxies: Vercel, then Render's own. The test says otherwise:

TestExpectedGot
14 failed logins in a minute, through Vercel429 after 10401 every time
Failed logins straight to Render429 after 10429
Straight to Render with a made-up X-Forwarded-ForCounted as you401: a forged header resets the count (a known gap)

Render answers with Cloudflare headers (cf-ray), so there is likely one more proxy than assumed. With 2, req.ip lands on Vercel's outgoing address, which changes from request to request: every attempt looks like a new visitor. Failed logins write nothing to the database, so the test was safe on staging.

Next: set TRUST_PROXY=3 in Render's dashboard, repeat the test, then repeat it from a phone on mobile data to prove two visitors get separate limits. Then write the value into render.yaml.
